# Eval options for live games

Research only. No code changed. The ADR that picks an approach comes later,
from these findings.

Scope: how LiveChess gets a chess engine evaluation (a centipawn or mate
score) per ply, live, for Slice 2 (eval number + win-probability bar on the
board page) and Slice 3 (a stored per-ply eval feeding a blunder/mistake
classifier). Constraint: **$0 budget**, one always-free VM (Oracle Cloud
Always Free or similar) for Postgres, Redis and the Bun processes, client on
Vercel Hobby.

## Summary

**Recommendation: a server-side Stockfish worker on the free VM is the
canonical eval source, with the PGN `[%eval]` comment used opportunistically
when the source already provides it (free, since it costs zero extra
compute).** The worker follows the versioned-job pattern already designed in
`docs/live-chess-app-architecture.md` (job carries `Game.version` at
creation, result discarded if the version has since moved on), so it never
blocks ingestion and never wastes work on positions nobody cares about
anymore. This is the only option that reliably produces one authoritative,
stored eval per ply for every live game, which is what Slice 3's classifier
needs (a classifier can't work off "whatever eval the last viewer's phone
happened to compute"). The PGN-eval shortcut costs nothing to check and
matters for specific broadcasts (see Option 1), but it cannot be the
primary mechanism because it is empirically almost never present for normal
human-relayed broadcasts, only for engine-vs-engine broadcasts like TCEC.

Runner-up: the server-side worker alone, skipping the PGN-eval shortcut for
now (one less code path) and adding it later only if CPU on the free VM
turns out to be tight. Cloud eval and browser-side Stockfish are not
recommended as the primary source; see their sections for why.

## What was actually checked

Live evidence, gathered 2026-09-24 with a handful of unauthenticated `curl`
requests (kept minimal per the task instructions):

- `GET /api/broadcast/round/SuD0awaS.pgn` and
  `GET /api/stream/broadcast/round/SuD0awaS.pgn` for the 46th FIDE Chess
  Olympiad, Round 8, a currently-live board-373+ match group. Across the
  whole round export (~1600 lines, dozens of games), **zero `%eval` and
  zero `%clk` comments** appeared anywhere, even in a game with moves
  already played (`1. e4 e6 2. d4 d5 *`). This is a lower-board match,
  almost certainly fed to Lichess as plain PGN without a DGT
  board/clock/engine feed behind it.
- `GET /api/broadcast/round/VezHR9zN.pgn` for a live TCEC (computer chess)
  broadcast. Every move carries both `[%eval ...]` and `[%clk ...]`, e.g.
  `1. e4 { [%eval 0.18] [%clk 0:30:00] } 1... c6 { [%eval 0.31] ... }`.
  TCEC's own relay already includes engine eval because the *players are
  the engines*; Lichess is relaying it, not generating it.
- `GET /api/cloud-eval?fen=...` for a mid-opening position (ply 15 of a
  real TCEC game): hit, `depth: 28`, `knodes: 16125`.
- `GET /api/cloud-eval?fen=...` for a specific middlegame position (ply 30,
  same game, no longer a book line): miss,
  `{"error":"No cloud evaluation available for that position"}`.

This directly confirms the coverage claims used below.

## Option 1: Eval already in the source PGN (`[%eval]`)

**How it works:** Lichess broadcasts are a relay. An organizer either
publishes a PGN file on a public URL that Lichess polls, or pushes PGN
updates via the API
(`POST /api/broadcast/round/{broadcastRoundId}/push`). Lichess does not
compute or inject engine evaluations into a broadcast's PGN itself; the
broadcast docs describe the round as built from "live-updating PGN files
produced by electronic chess boards or other sources", and the API spec's
Broadcasts section describes push/pull of PGN with no mention of Lichess
adding analysis
([lichess.org/broadcast/help](https://lichess.org/broadcast/help);
[github.com/lichess-org/api, lichess-api.yaml](https://github.com/lichess-org/api/blob/master/doc/specs/lichess-api.yaml),
"Broadcasts" tag description). Separately, about 6% of *regular* Lichess
game exports on the public database include `%eval` from Lichess's own
post-hoc cloud analysis, unrelated to broadcasts (community-sourced figure
from a Lichess database discussion; **unverified against a primary Lichess
statement**, treat as approximate).

So whether a broadcast round's PGN carries `%eval` depends entirely on the
**source feed**: some electronic-board vendors and DGT-based relays include
live engine analysis from their own hardware/software; most human
tournament relays (as confirmed live above, for an Olympiad round) do not;
engine-vs-engine events like TCEC always do, because the eval *is* the
data, generated by the competing engines.

Our current parser (`server/src/ingestion/lichess.ts`) already tokenizes
brace comments for `%clk` and silently discards everything else in the
comment body, so an `%eval` token flowing through today is simply dropped,
not an error (see the `ITEM_RE`/`CLOCK_RE` handling around
`parseMovetext`).

- **Cost:** $0, it's free text already in the stream we consume.
- **Latency:** none, arrives with the move itself.
- **Coverage:** confirmed empirically as unreliable for the broadcasts
  LiveChess is actually built for (elite human events). Reliable only for
  engine-vs-engine broadcasts and for whatever subset of organizers push
  DGT/engine-fed PGN with eval baked in. **Cannot be assumed present.**
- **Limits:** none beyond "may not be there."
- **Licensing:** none, it's just PGN text.
- **Effort:** trivial. Extend `CLOCK_RE`-style parsing in `lichess.ts` to
  also capture a `[%eval ...]` token per move (`ParsedPly` gets an optional
  `eval` field), store it as an already-known value, and skip queuing an
  eval job for that ply.
- **Serves Slice 2:** yes, whenever present, at zero latency.
- **Serves Slice 3:** only for the (small) subset of games where it's
  present for every ply; can't be relied on as the classifier's sole input
  since most human broadcasts won't have it.

## Option 2: Lichess cloud eval API (`GET /api/cloud-eval`)

**How it works:** returns the cached Stockfish evaluation for a FEN,
"opening positions have more chances of being available", the note being
that overall there are about 320 million positions in the database, up to
`multiPv` (max 5) lines, variants supported
([github.com/lichess-org/api, api-cloud-eval.yaml](https://github.com/lichess-org/api/blob/master/doc/specs/tags/analysis/api-cloud-eval.yaml)).
404 with `{"error": "..."}` on a miss (confirmed live above).

- **Cost:** $0, unauthenticated GET.
- **Latency:** one HTTP round trip, low when it hits.
- **Coverage:** confirmed empirically poor for the case that matters
  (a specific elite game's middlegame position). The endpoint's own docs
  steer this: "opening positions have more chances of being available" and
  explicitly say to use it for "a few positions here and there", pointing
  bulk users at the [exported eval database](https://database.lichess.org/#evals)
  instead. A live elite game diverges from known book within a handful of
  moves, at which point the exact position is usually unique to that game
  and won't be cached unless someone happened to analyze that exact
  position on Lichess before.
- **Limits:** no documented per-minute number specific to this endpoint.
  The general API docs warn "Unauthenticated endpoints are heavily
  rate-limited and might stop functioning"
  ([github.com/lichess-org/api, lichess-api.yaml Broadcasts tag description](https://github.com/lichess-org/api/blob/master/doc/specs/lichess-api.yaml),
  referencing [lila PR #21283](https://github.com/lichess-org/lila/pull/21283)).
  There have been user reports of hitting 429s on cloud-eval specifically
  ([lila issue #18781](https://github.com/lichess-org/lila/issues/18781)).
  **Exact limit for cloud-eval: unverified.**
- **Terms of use for a third-party app:** no explicit "you may not build a
  live eval feature on this" clause found; the endpoint's own description
  effectively discourages relying on it as a primary bulk source. Using it
  as an opportunistic early-game freebie (first few plies, known openings)
  is consistent with its documented intent; using it as the backbone for
  ~800 concurrent games' worth of live eval is not.
- **Licensing:** N/A, it's a hosted API response.
- **Effort:** trivial to call, but needs a fast fallback path for the
  (common) miss case, so it can't stand alone.
- **Serves Slice 2:** only for the opening portion of a game, and only
  until the position diverges from cached lines, so the eval bar would
  frequently go blank or stale mid-game if this were the only source.
- **Serves Slice 3:** not reliable enough on its own; the classifier needs
  an eval at *every* ply to compute swings, and most non-opening plies
  won't be cached.

## Option 3: Stockfish in the viewer's browser

**How it works:** run a WASM build of Stockfish as a Web Worker in the
client, feed it the current FEN, read back an eval.

Two relevant builds:

- **lichess-org/stockfish.wasm**: GPL-3.0
  ([repo](https://github.com/lichess-org/stockfish.wasm), "Thanks to the
  Stockfish team for sharing the engine under the GPL3"). Needs
  `Cross-Origin-Embedder-Policy: require-corp` and
  `Cross-Origin-Opener-Policy: same-origin` on the page (SharedArrayBuffer
  requirement for the multi-threaded build). Total ~400KB (~150KB gzipped)
  across `stockfish.js` + `.wasm` + `.worker.js`. Explicitly **no NNUE
  support**: it's a classical-eval fork, marked "passively maintained" in
  its own README, with current work moved to a separate `stockfish-web`
  port. Weaker eval quality than modern NNUE Stockfish as a result.
- **nmrugg/stockfish.js**: GPL v3 (`Copying.txt` in the
  [repo](https://github.com/nmrugg/stockfish.js)). Five build flavors:
  large multi-threaded (~94MB, needs CORS/COOP-COEP), large single-threaded
  (~94MB, no special headers needed but single-core speed only), lite
  multi-threaded (~1.6MB, needs CORS/COOP-COEP), lite single-threaded
  (~1.6MB, no special headers), and an asm.js fallback (~3MB, pure JS, no
  WASM). The single-threaded flavors skip SharedArrayBuffer/COOP-COEP
  entirely at the cost of using one core.

- **Cost:** $0, runs on the viewer's device.
- **Latency:** depends entirely on device. A phone's single core reaching
  a useful depth (say 16-20 ply) in 1-2 seconds is plausible with the lite
  NNUE build but **not verified this session with a real benchmark**; older
  or low-end phones will do noticeably worse, and background-tab
  throttling on mobile makes this unreliable when the viewer isn't looking
  at the tab.
- **Coverage:** 100% of positions, no cache miss, but quality/depth is
  bounded by the device, not by us.
- **Limits:** CPU and battery cost sits on the viewer's device, which
  matters more on a phone watching a multi-board grid (Slice 2 also wants
  a "watch a whole round at once" view, which would mean N simultaneous
  Stockfish workers on one device if this were the approach).
- **Licensing:** GPL-3.0. Loading the WASM/JS as a separate file via a Web
  Worker (its own documented message-passing interface, not code linked
  into the app's own JS bundle) is the standard pattern every major chess
  site uses (Lichess itself, and others) and is generally treated as
  "mere aggregation"/a separate program communicating over a defined
  protocol rather than a combined work, per the general GPL FAQ discussion
  of pipes/sockets as normal separate-program communication
  ([gnu.org GPL FAQ](https://www.gnu.org/licenses/old-licenses/gpl-2.0-faq.en.html)).
  That FAQ also cautions that sufficiently "intimate" communication could
  still count as combining the works. **This is not legal advice and the
  exact boundary is a judgment call**; the safe, well-precedented pattern
  is: ship the engine as its own unmodified file(s), talk to it only over
  its UCI-over-postMessage interface, include its license text, and link
  to its public source, none of which requires relicensing the rest of the
  (Apache-2.0) app.
- **Effort:** moderate. New dependency, a worker-loading path, and for the
  multi-threaded NNUE build, COOP/COEP headers on the Vercel-hosted client.
  Vercel supports custom response headers via `vercel.json`
  ([vercel.com/docs/headers](https://vercel.com/docs/headers)); no
  Hobby-tier restriction on setting them was found, but a Hobby-specific
  confirmation for COOP/COEP specifically is **unverified**. The
  single-threaded lite build sidesteps this entirely at a speed cost.
- **Serves Slice 2:** yes, for whoever is currently looking at a board, at
  the cost of their device's battery, and with weaker eval quality unless
  the heavier multi-threaded NNUE build is used.
- **Serves Slice 3: does not serve this at all as designed.** The
  classifier needs one canonical eval per ply stored server-side, not a
  per-viewer, per-device number that only exists while somebody's browser
  tab happens to be open and foregrounded. This option does not produce
  anything durable.

## Option 4: Server-side Stockfish worker on the free VM

**How it works:** run the native Stockfish binary as a child process, talk
UCI over stdio, feed it FEN + a fixed movetime/depth budget, read back
`info depth ... score cp/mate ...`, store the result.

- **Cost:** $0, it's compute already paid for by the always-free VM.
- **Licensing:** GPL-3.0
  ([official-stockfish/Stockfish](https://github.com/official-stockfish/Stockfish)).
  Running the official binary as a separate OS process invoked over its
  documented UCI text protocol, not statically linked into the Bun
  process, is the same "mere aggregation via pipes" pattern as Option 3
  and is how essentially every third-party chess product (commercial GUIs
  included) has used Stockfish for years. Ship the binary unmodified,
  include its `COPYING`/license file and a link to
  [official-stockfish/Stockfish](https://github.com/official-stockfish/Stockfish),
  and the rest of the codebase stays Apache-2.0. **Not legal advice.**
- **Latency:** one process round-trip per position, tunable via
  `movetime`/`depth`. A shallow, fixed movetime (e.g. 200-500ms) is enough
  for a live eval bar; deeper search costs more CPU per position, directly
  trading off against how many concurrent games one small VM can keep up
  with.
- **Throughput / capacity, worst case:** ~8 followed rounds x up to 100
  games each is up to ~800 games live at once, each producing a new ply
  roughly every 10-60+ seconds depending on time control (bursts near time
  scrambles). One important, easy-to-miss update since the architecture
  doc's Oracle-Ampere assumption: **Oracle quietly cut the Always Free
  Ampere A1 allotment from 4 OCPU/24GB to 2 OCPU/12GB around June 2026**,
  now billed as a 1,500 OCPU-hour / 9,000 GB-hour monthly pool splittable
  across instances, plus two small AMD Micro VMs (1/8 OCPU, 1GB each), 200
  GB block storage, 10TB egress
  ([InfoQ](https://www.infoq.com/news/2026/07/oracle-cloud-free-tier-limits/);
  [cloudpricecheck.com/free-tier/oracle](https://cloudpricecheck.com/free-tier/oracle)).
  Nodes-per-second figures for modern Stockfish are hardware-dependent and
  **not independently re-benchmarked this session**; a third-party
  estimate (not an official Stockfish source) puts a typical 4-core
  consumer machine around 5 million nodes/sec
  ([chessify.me blog](https://chessify.me/blog/nps-what-are-the-nodes-per-second-in-chess-engine-analysis)),
  i.e. roughly ~1-1.5M nodes/sec/core as a rough order of magnitude, which
  at a shallow fixed movetime (a few hundred ms) is a small fraction of a
  CPU-second per position. On 2 OCPUs, a queue that processes a few
  positions per second per core at shallow depth is well within budget for
  realistic average move rates across 8 rounds; a worst-case simultaneous
  burst across all ~800 games would need to shed load by depth or by
  dropping the oldest queued job, which the version mechanism already
  supports. **Treat this as a rough estimate, not a benchmark**; a
  same-VM `stockfish bench`/`speedtest` run before committing would
  de-risk this.
- **Queue design:** the architecture doc already specs the exact mechanism
  needed: an Eval Job carries `job.version = Game.version` at creation;
  when the worker finishes, if `job.version != current Game.version` the
  result is discarded, because a newer move or a correction has already
  superseded it (`docs/live-chess-app-architecture.md`, "Versioned jobs"
  section and invariant #6). This means a backlog under load doesn't need
  special-casing: stale jobs for positions nobody cares about anymore are
  cheap to detect and drop, and only the queue depth/worker concurrency
  needs tuning. The doc names BullMQ for this; `bullmq` is **not yet a
  dependency** (`server/package.json` currently has `ioredis`,
  `drizzle-orm`, `postgres`, `chess.js`, `zod`, ADR/none for the queue
  choice yet), so this is a real new-dependency decision, not a given, and
  a simpler Redis list/stream built on the already-present `ioredis` client
  is a smaller-footprint alternative worth weighing in the ADR.
- **Effort:** moderate. Needs: the Stockfish binary on the VM (a build
  step or package, e.g. `apt install stockfish` or a static build), a
  worker process that pulls jobs, talks UCI, writes results; a schema
  change (`moves` currently has no eval column,
  `server/src/db/schema.ts`), and either BullMQ or a lighter queue on
  Redis. All net-new work, but it fits the existing outbox/versioned-job
  shape the architecture already committed to, so it's additive, not a
  redesign.
- **Serves Slice 2:** yes, pushed live through the same outbox → Redis
  stream → gateway path moves already use, per the architecture's
  "Live win-probability bar" mapping (`docs/live-chess-app-architecture.md`,
  Feature → Architecture Mapping).
- **Serves Slice 3:** yes, this is the only option that produces a durable,
  canonical eval per ply in Postgres, which is exactly what a swing-based
  classifier needs.

## Option 5: Hybrid

Use whichever cheap source is already correct, fall back to the worker:

1. If the ingested PGN comment already carries `[%eval ...]` for a ply
   (Option 1), store it directly, skip the worker for that ply. Free, and
   it's the exact value the source considers authoritative (relevant for
   engine broadcasts like TCEC, and any organizer feed that happens to
   include it).
2. Otherwise, for early-game plies still in known opening theory, an
   opportunistic `cloud-eval` lookup (Option 2) *may* hit and save a
   worker job; treat a miss as the normal case, not an error.
3. If the position has 7 pieces or fewer, ask the Lichess tablebase
   (see "Other Lichess endpoints checked"): an exact result, no CPU.
4. Otherwise, queue a server-side Stockfish job (Option 4), versioned per
   the existing pattern, as the reliable fallback that always eventually
   produces a value.
5. The browser-side engine (Option 3) stays out of the server-stored path
   entirely; it could still be offered later as an opt-in "deeper local
   analysis" toggle for someone actively staring at one board, but that is
   a separate, additive feature, not part of how the stored per-ply eval
   gets made.

This is what the recommendation above is: steps 1 and 4, with steps 2 and 3 as
optional, low-priority additions. It costs nothing extra to check the PGN
comment first (already parsing the comment stream) and nothing extra to
try a cheap cache lookup before falling back to compute, but it does add
code paths and edge cases (what if the PGN eval and a later worker
recompute disagree; do we trust an organizer's engine settings). The
runner-up recommendation (worker only, skip 1 and 2 initially) trades a
small compute cost for a simpler first version.

## Other Lichess endpoints checked

Every endpoint in the Lichess OpenAPI spec (`docs/Lichess API 1.json`)
that mentions eval, engines or analysis, checked on 2026-09-24.

**Cloud eval, more detail** (`GET /api/cloud-eval`, spec in
`docs/Lichess API 1.json`): about 320 million cached positions, up to 5
lines. A live check for the position after 1. e4 e5 2. Nf3 returned depth
65 with `cp: 18`, so opening positions really are covered deeply. The
general rate-limit rule in the same spec is "Only make one request at a
time" and "wait one minute" after a 429. That makes it a good fit for the
first plies of a game through a single serialized queue, and a bad fit
for every ply of hundreds of games.

**Tablebase** (`GET https://tablebase.lichess.org/standard?fen=...`):
exact results for positions with 7 pieces or fewer. A live check on a
K+P vs K+P position returned `category: "win"`, `dtm: 17` (mate in 17)
and the winning moves. This is better than any engine for endgames: an
exact win, draw or loss instead of an estimate, and zero CPU on our VM.
Same one-request-at-a-time rule applies. Late endgames change slowly
(few games reach 7 pieces at once), so the request rate is low.

**Eval database dump** (`https://database.lichess.org/lichess_db_eval.jsonl.zst`,
linked from the cloud-eval description): the whole cloud-eval cache as
one file. A HEAD request shows 22 GB compressed (last modified
2026-09-10). Far too large for a free VM's disk and memory, so not an
option.

**Opening explorer, masters** (`GET https://explorer.lichess.org/masters`):
no eval, but gives the opening name and how often each move was played in
master games, with results. Not a source for the eval bar. Could be useful
later for commentary ("still in theory", opening name on the board page).

**External engine** (`/api/external-engine/...`): this lets you register
*your own* engine so it can be used from the Lichess analysis board. The
analysis still runs on hardware you provide, so it gives no free compute.
Not useful here.

**Broadcast PGN `comments` parameter** (round export and round stream):
`comments=true` is the default and includes comments "when available",
with `12. Bxf6 { [%eval 0.23] }` as the example. This confirms Option 1:
Lichess passes along whatever eval the source feed contains and does not
compute any itself.

## Open questions for the owner

1. **Depth/movetime budget for the live eval bar.** A shallow, fast eval
   (good enough for a win-probability bar) versus a deeper one (better for
   the Slice 3 classifier's blunder detection) may want different
   settings; is one shared shallow eval per ply enough for both, or does
   the classifier eventually want a second, deeper pass?
2. **BullMQ vs. a lighter Redis-based queue.** The architecture doc names
   BullMQ, but it isn't a dependency yet and the project already has
   `ioredis`. Worth a real decision, not just inheriting the original spec
   sketch, especially since BullMQ's Node-only worker model isn't a given
   fit with a Bun runtime and single-VM free-tier target.
3. **Whether to trust an organizer-supplied `%eval` at all**, or only ever
   use it for known engine-vs-engine broadcasts (TCEC-style) and always
   recompute with our own Stockfish for human events, to keep every
   number's provenance consistent for the classifier.
4. **What "good enough" depth actually looks like on 2 OCPU**, now that
   the Oracle Always Free Ampere allotment has been halved. A real
   `stockfish bench`/`speedtest` run on a representative free-tier
   instance, before committing to a depth/movetime budget in the ADR,
   would replace the rough nodes-per-second estimate above with a real
   number.
5. **Whether the eval column lives on `moves`** (one row per ply already
   exists) **or a separate `evals` table** keyed by `(game_id, ply)`, given
   `moves` rows are never deleted/only superseded (ADR 0001, ADR 0004) and
   an eval could in principle be recomputed/corrected independently of the
   move itself.
6. **Multi-board grid battery cost.** Slice 2 also wants a "watch a whole
   round at once" grid. If browser-side Stockfish is ever added as an
   opt-in extra later (not the stored path), running N engine instances on
   one device for a grid view is a real constraint worth deciding against
   explicitly now rather than discovering it later.
